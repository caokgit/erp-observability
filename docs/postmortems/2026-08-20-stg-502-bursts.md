# Post-mortem: 2026-08-20, stg's pages went blank, then the TV dashboards failed

Status: written 2026-11-08 from the workspace (S4); for the
ERP and platform teams' review. Sources: the platform workspace (`ContainerAppConsoleLogs_CL`: nginx and Odoo lines of
stg's web app; `ContainerAppSystemLogs_CL`: its probes, kills and revisions), the `RestartCount` metric, the rules'
backtests ([kql/backtest.py](../../kql/backtest.py)), and the platform team's same-day write-up of the morning (the
owner's infra notes, outside this repo: Postgres errors, CPU, the request that hung). Nobody is named; all times UTC. Template: [method/templates/postmortem.md](../../method/templates/postmortem.md).

## Summary

On 2026-08-20 stg's web app failed three times. **Morning:** a write started from the Sync screen waited on a lock with
no time limit; with all of the web app's Odoo workers blocked, the health probe timed out and Azure killed the container,
twice in 12 minutes; every request in flight got a 502 (84, then 113). **Afternoon:** for about 1.5 hours workers kept
dropping requests mid-answer (502s, users giving up) through a deploy at 09:07. **Evening:** after another deploy at
10:23, every TV dashboard poll got a 500 for about 40 minutes. Nobody was alerted; users reported the blank pages. A lock
timeout for Odoo's role (2026-08-25) and round 1's rules (live 2026-11-08) have changed the picture since; one gap,
probe kills that no rule paged, is closed by this post-mortem.

## Contributing causes

The morning, as a chain (measured, except where marked):

1. A write from a button in the UI asked Postgres for a row lock **with no time limit**, during heavy contention
   (Postgres' error counts above).
2. Odoo serves each request on one worker process, synchronously; a blocked query blocks its worker. stg's web app ran
   few of them (the startup log: 6 processes in the container).
3. With every worker blocked, the process could not answer the liveness probe's TCP connect within 5 s (inferred from
   the timing; the write-up marks the exact mechanism as not proven).
4. Three failed probes in a row: Azure Container Apps kills and restarts the container, by design.
5. For 13 s nothing listened; nginx answered every request in flight with 502.

Gaps that let it reach users: no lock or statement timeout for the app's role (fixed 2026-08-25); a write that can
block run inside a web request; no alert on lock waits, on 5xx bursts or on probe kills.

The afternoon and the evening are **not explained** by the data: the afternoon's worker ends without a kill fit
Odoo's own worker limits (a request over its time limit is killed by Odoo's master), which only Odoo's log file would
show (it reaches back to 2026-10-31 only, [odoo-logs](../learn/odoo-logs.md)); the evening's TV failures began with
a revision update and ended without one, which fits code deployed before its database update ran (a module upgraded
later), but only the ERP team's deploy record can say. Both are questions for the ERP team below, not conclusions.
